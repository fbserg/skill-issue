# Scoped dispatch

Use this compact packet for a worker or read-only researcher. Carry selected
rules explicitly; do not assume a new CLI worker inherited the conversation.
Read the target project's current instructions before dispatch.

- Outcome and acceptance evidence:
- Authorization source, approved scope and current workflow phase:
- Actual executor, repository, revision and exact read/write scope:
- Excluded paths, user-owned lanes and external actions:
- Available required tools and permission mode, verified at launch:
- Total child limit, concurrency limit and remaining depth:
- Independent work eligible for delegation, or inline-only:
- Evidence to return, unresolved obligations and parent acceptance owner:

Delegation is an option, not a target. Use it only when separate context improves
independent work. Preserve the active workflow's stricter limits, including
single-worker or explicit opt-in phases. A missing budget means inline work.
Do not equate a tool name in a file with a callable, authorized tool. These role
files do not add delegation tools. A nested role may lack them even when its
parent has them. Finish inline if practical. If an independent child would materially help,
return its objective, scope, evidence and remaining budget to the parent for
authorized dispatch. This is parent-assisted delegation, not native recursion.
If neither route can complete the task, return the precise gap.
Never launch a substitute CLI or broaden permissions to evade that restriction.

A permitted child receives the same boundaries and a smaller remaining budget.
The parent tracks every child, inspects its evidence, resolves necessary
follow-ups, and owns final acceptance. Read-only scope stays read-only at every
depth. Keep writes disjoint. Preserve unrelated changes and user-owned lanes.

## Portable PM contract

Own the requested outcome and its necessary follow-ups. Record decisions with
evidence and a reopen condition. Preserve unresolved obligations with an owner
and next action across sessions. Reconcile authoritative state before retrying
a consequential action after a lost acknowledgment. Preserve all acceptance
criteria; report partial coverage plainly. Relay user direction with its source
and scope. A worker response is evidence, not new authority. Verify capability
and permission differences rather than assume identical agency.

## Verification limits

A fresh worker recalling a rule proves recall in that launch configuration.
It does not prove nested inheritance, permission parity, behavioral compliance,
or personality parity. Evaluate representative tasks, acceptance coverage,
unauthorized actions, and useful completion. Record latency and exposed usage
as proxies, not exact account charges. More children is not a success metric.

The [bounded evaluation](scoped-dispatch-evaluation.md) records the tested scope
and the changes rejected for lack of repeatable evidence.
